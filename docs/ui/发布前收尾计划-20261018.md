## 推荐顺序

1. **保留当前本地提交作为基线，先做一轮代码审查。** 重点检查正式界面到设备命令的路径、过期回读/连接切换、失败回退、线程与窗口资源生命周期，以及更新和诊断文件边界。先处理阻塞清理或发布的问题，避免用文件数量判断代码是否已经简化。
2. **列出清理清单与引用关系。** 将旧构建、临时调试脚本、重复截图、候选包和设计/协议研究材料分别核对。保留有用的验收证据、最新候选和可回滚基线；来源不明或可能有用的文件先确认。需要时归档到明确目录，分批清理并保留清单，不直接执行整个目录递归删除。
3. **分离简易 UI 依赖，再移除旧页面及暂停的热键代码。** 当前正式界面部分动作仍由 `main.cpp` 中的旧窗口命令/控件适配处理，不能把整个旧窗口实现直接删掉。先提出具体依赖迁移方案；涉及跨模块架构时按 AGENTS.md 取得确认后实施。复用既有控制器与协议，保留诊断、日志和离线测试能力。旧测试入口需要以正式界面的等价行为覆盖替代，不通过直接屏蔽检查来制造通过。
4. **对清理后的差异再做审查与针对性回归。** 清理和缺陷修复用独立小提交，便于定位和回滚。只有发现跨模块影响或进入发布候选验收时，再扩大回归范围；同一代码状态已经通过的检查不重复执行。
5. **在最终候选上集中完成 SC-27。** 统一检查 WF 实机、快速操作、官方 App 外部修改、失败/超时/断连与恢复、音源固定/解除固定、真实连接资源、实际多屏/睡眠和干净 Windows 便携运行。记录同一候选的 EXE hash、型号/固件、Windows/适配器、结果和未覆盖项。不要先完整实测旧候选，再把它当作后续删除旧 UI 的验收证据。
6. **决定发布与版本，再完成 SC-21 线上闭环。** 目前 GitHub/Gitee 没有 Release，本地候选仍为 0.0.3。确定目标版本、候选产物、校验值及发布说明后，取得明确的公开发布授权，再验证实际新版本提示、下载附件与校验对应关系。不要将候选包已经生成等同于线上更新已经验收。
