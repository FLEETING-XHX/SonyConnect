# SonyConnect 模块化架构与分阶段开发

记录日期：2026-10-09。状态：用户确认的开发约束与架构计划，尚未创建应用代码。

## 1. 开发约束（用户确认）

项目采用模块化设计。初期先使用简易 UI 开发和验证主要功能；主要功能完成并通过验收后，再切换到已经设计好的 UI，最后调整动效与视觉细节。

简易 UI 与正式 UI 使用同一套设备状态、业务操作和协议实现。更换界面时保留已经验证的功能模块，不重新编写耳机控制逻辑。现有 pen 设计及 [功能与交互说明](功能与交互说明.md) 继续作为最终界面的目标。

当前仍保留中文优先、常驻托盘、WF / WH-1000XM5、自包含单 EXE 和较低资源占用的产品目标。模块先按责任划分，根据实际复杂度决定是否拆成独立程序集；模块化本身不要求增加常驻进程。

## 2. 模块边界

| 模块 | 责任 | 边界 |
| --- | --- | --- |
| 设备与状态模型 | 型号、固件、能力、连接状态、电量、音源、声音模式、EQ、未知值与失败原因 | 不依赖 WPF 控件、Windows 蓝牙对象或动画 |
| Sony 协议 | 封包、解析、握手消息、能力查询、命令字段与协议版本适配 | 面向字节与协议消息；不决定窗口、文案或动画 |
| 蓝牙传输与会话 | Windows RFCOMM 服务发现、字节收发、连接生命周期、取消、超时、重连和资源释放 | 经接口提供传输；协议层负责帧处理，会话层统一协调请求与通知 |
| 应用操作与状态协调 | 读取设置、修改模式、EQ、设备切换等用例；请求中 / 成功 / 失败 / 回退；设备事件同步 | 对 UI 提供操作与状态；不使用窗口控件，也不直接处理视觉效果 |
| Windows 集成 | 耳机输出端点音量、媒体会话、全局快捷键、托盘与工作区信息 | 将系统行为转换为应用接口；耳机协议和系统音频状态分别处理 |
| 设置与更新 | 本机偏好、快捷键草稿与保存、样式选择、版本比较及 Releases 目标 | 不把 UI 样式偏好写入耳机；更新请求异步执行 |
| 诊断与验证 | 分层日志、命令关联编号、录制 / 回放、模拟传输、故障场景及回归测试 | 无耳机时可验证状态与解析；模拟结果和实机结果分别记录 |
| 呈现层 | ViewModel、简易视图、正式视图、样式资源、输入反馈与动画 | 调用应用操作、展示状态；不在按钮事件中拼协议或建立蓝牙连接 |

建议代码组织：Core（模型与协议）、Application（用例、会话协调及服务接口）、Infrastructure（Windows 与持久化等实现）、Presentation（ViewModel 与视图）、App（组合入口与生命周期）。目录 / 项目名称可随实现调整，责任与依赖方向保持明确。

依赖方向：Core 不依赖上层；Application 使用 Core 并定义其需要的服务接口；Infrastructure 实现接口；Presentation 使用 Application 提供的操作和状态；App 负责组装。Windows 类型与 WPF Dispatcher 留在相应适配层。

## 3. 共用接口与状态规则

- 传输通过接口替换为真实 RFCOMM、模拟收发或录制数据回放；这些实现使用一致的字节接口。设备控制、媒体控制、音量、设置存储与更新查询也明确接口边界。
- 用例接收动作和参数，返回操作结果；设备状态由确认、回读与通知更新。UI 动画结束不代表耳机执行成功，按钮点击也不直接改成已确认状态。
- 请求中、断开、不支持、未知、读取失败和写入失败均有明确表示。未知值不默认为关闭或零；失败恢复最后确认状态，并提供可理解的原因。
- 每次连接标识当前设备与会话，设备更换后清空旧读数，忽略过期会话的迟到响应。外部触摸、官方 App 修改、音源切换与重连都通过统一状态更新路径同步。
- 请求顺序、ACK、超时、取消与通知按协议分别协调。耗时操作异步执行；UI 线程和快捷键输入回调不等待蓝牙响应。
- 两种 UI 共用应用状态与操作，视图切换保留数值和错误处理。线程调度、窗口位置与动画留在呈现 / 桌面适配层。
- 日志贯穿连接、请求、响应和状态更新；开发初期即可导出诊断记录。复现步骤、型号、固件与验证结果随功能记录。

## 4. 阶段 A：基础框架与简易 UI

先建立连接、协议、状态和诊断的最小链路，再逐项扩展功能。

简易 UI 使用标准控件：设备选择与连接按钮、状态 / 电量文字、声音模式按钮、普通滑块、设置开关、媒体控制和错误提示。只提供验证功能需要的布局与反馈，复杂动画、四窗口排布和轨道外观切换放到正式 UI 阶段。

简易 UI 操作真实业务接口，能够观察请求、响应、回读和失败；新增一项功能，同时增加必要的状态展示和诊断入口。模拟模式应明确标识，不能作为实机成功验收。

## 5. 阶段 B：完成并验证主要功能

主要功能按现有需求逐项实现，建议验收顺序如下：

| 顺序 | 功能范围 | 验收重点 |
| --- | --- | --- |
| 1 | 设备发现 / 选择、控制连接、固件与能力、电量 | 正常连接、音频与控制连接区别、断开重连、未知读数与换设备清理 |
| 2 | 降噪 / 通透 / 关闭、环境声音强度、关注语音 | 写入确认、回读、外部操作同步与模式依赖 |
| 3 | 五段 EQ、预设、CLEAR BASS | 合法整数范围、预设与自定义一致、失败回退 |
| 4 | 本机耳机音量、媒体标题与播放控制 | 音量双向同步；无媒体、外部音源和不支持的操作正确反馈 |
| 5 | 双设备开关、设备列表、当前音源与普通切换 | 按能力验证；区分普通切换与固定播放，拒绝 / 断开后状态一致 |
| 6 | 耳机关机、必要的软件设置与托盘生命周期 | 正确命令与状态反馈；退出释放连接、订阅和后台任务 |

固定播放、DSEE、提示音量、触摸功能分配、R-Ctrl+F1～F3、更新检测等继续按需求和能力推进，记录各自验证状态。某功能缺协议或测试条件时，说明缺项及限制，不使用空按钮或静态值假装完成。

WF 与 WH 分别记录能力和测试结果；只验证一个型号时，不宣称另一型号已验证。协议研究依旧遵循 [研究路线](协议研究路线与资料索引.md)：开源定义 / 实现 / 测试为主，APK 补缺，实机验收。

## 6. 进入正式 UI 的条件

切换前需逐项满足并记录：

- 主要功能在简易 UI 中已完成真实链路：操作、请求、确认 / 回读、状态显示及失败处理。
- 目标型号与固件的实机结果已记录；未支持、未验证和受限功能有明确状态。
- 连接断开、超时、重连、取消、外部状态改变和连续操作的关键场景已验证。
- 协议解析与状态协调的关键问题具有必要的离线回归或模拟用例，可在更换 UI 后重复验证。
- 简易 UI 已建立功能基线，包括日志与操作步骤。先解决阻塞主要功能的问题，再投入正式视觉实现。

验收以真实行为为准。模拟测试通过、界面可点击或控件显示正常，均不能单独代表主要功能完成。

## 7. 阶段 C：切换设计 UI 与动效

逐个替换视图、模板和资源，接入现有 ViewModel / 应用服务。按照 pen 和交互说明完成窗口排布、状态预览、可视样式选择与动效；保留简易 UI 作为开发期诊断入口或构建选项，不复制业务逻辑，也不强制对最终用户显示调试入口。

正式 UI 应重复阶段 B 的同一组操作与回归，重点检查命令数量、事件顺序、写入频率、焦点、动画取消、视图关闭与资源释放。禁止在动画中逐帧发送命令；Wake / Elastic 样式选择不改变合法参数范围和 stepped 规则。

性能验收覆盖空闲托盘、窗口隐藏、拖动、动画与重连。发布阶段检查单 EXE、自包含运行、体积、内存与 CPU，再确定优化措施；文档不预先承诺未经测量的占用值。
